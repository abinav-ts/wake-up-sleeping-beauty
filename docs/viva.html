Viva Sheet

Wake Up, Sleeping Beauty: an alarm clock that punishes oversleeping with unpredictable alarms.

The idea in one paragraph

You set alarms in the app. If you let one ring (or snooze it) for x minutes, then any alarm you set for 24 hours or more after that ring is moved by a hidden random amount, earlier or later, whose size grows with x. You can't see the real time. The only way out is to walk 10,000 steps (read from Apple Health) before the shifted alarm fires.

Architecture

iPhone PWA  ──(X-Device-Id)──►  Worker /api/*  ◄──►  D1 (alarms, chaos, subs)
    ▲                          ▲   │
    │ push notification        │   └── cron (every minute): start due alarms,
    │                          │        send a push every ~30 s until Stop/Snooze
Apple push service ◄───────────┘
iOS Shortcut (Health steps) ──► POST /api/steps?u=<id>

The Worker is the only place the real fire time exists. /api/state never selects it, so the client cannot show or leak it (there is a test for that).

The chaos logic

1. Measure x. When you stop an alarm, x = minutes rung (snoozes included) minus a 3-minute reaction grace, never below 0. An alarm nobody answers auto-stops after 30 minutes, so x is capped at 27.
x = max(0, min(stop − ringStart, 30 min) − 3 min)
2. Start the 24h clock. T1 = when that alarm started ringing. Alarms whose intended time is at or after T1 + 24h are "affected".

3. Draw the shift. Normal, centred on zero, so earlier and later are equally likely, with spread proportional to x and no hard cap:
s ~ Normal(0, σ²), σ = 15 min × x
fire = max(intended + s, now + 1 min)
Generated with Box–Muller from the browser-grade crypto RNG. The now + 1 min floor only stops a shifted alarm landing in the past.

4. Keep it hidden and fair. The draw happens on the server: at creation for new alarms, or when an earlier alarm finishes (pending alarms are re-rolled with the new x). Several alarms get independent draws, but you can't see any of them.

5. Escape. If steps since T1 reach 10,000 before the shifted alarm fires, the shift is cancelled and the alarm rings at the intended time (immediately, if that time has already passed).

6. Chain. Every alarm that rings replaces the chaos state (new T1, new x).

Worked example. Let an alarm ring 12 minutes: x = 12 − 3 = 9, σ = 135 min. Then P(moved by more than 30 min) ≈ 82%, more than 2 hours ≈ 37%, more than 6 hours ≈ 0.8%. A 1-minute reaction after the grace gives x = 0, so no shift at all.

Identity and multi-user design

No login, one key. On first launch each browser generates a random 128-bit ID and stores it locally. Every request carries it as X-Device-Id, and every table (alarms, chaos_v2, subs) is keyed by it, so users never see or affect each other's data. Guessing a valid ID is infeasible (2128 possibilities).

Fair play at scale. The cron job handles everyone's alarms in one pass, and pushes go only to the owner's devices. Because signup is free, there are guard rails: 20 new devices per IP per hour (IPs stored only as a truncated hash), 2000 users, 25 open alarms each, alarms at most a year out, and users unseen for 90 days are purged.

Recovery. The ID lives in the app's storage, so clearing it loses the alarms. The app can copy the ID and restore it on a new phone.

Migration. The earlier single-token version's data is moved to the owner's new ID the first time their old browser presents the old token; after that the token can be deleted.

Design decisions and trade-offs

  • We own the alarms. iOS gives apps no access to the Clock app's alarms, so alarms are created in this app.
  • Web, not native. A project constraint. The cost: no HealthKit and no true alarm ringing, so we use Shortcuts and a push "nag loop".
  • Normal distribution. Symmetric, one parameter, unbounded tails (as requested), and easy to explain and test: mean 0, sd 15·x, checked statistically in a unit test.
  • Empty-payload push. The service worker shows a fixed "Wake up!" notification, so there is nothing to encrypt, which removes the most error-prone part of Web Push.
  • Cron every minute. Granularity is one minute, so an alarm may start up to 60 s late. A second push goes out 30 s after the first.
  • D1 over KV. Strongly consistent reads and writes for a read-modify-write workload.

Honest limitations

  • Push delivery on iOS can be delayed, and Silent mode or Focus will mute it. Keep a real backup alarm.
  • Steps arrive when the Shortcut runs (e.g. every few hours), so a goal reached between runs may be noticed late. The number is sent by a Shortcut, so the check is honest-system, not tamper-proof.
  • Setting a backup alarm earlier than T1 + 24h is unaffected by design.
  • The device ID is the only key: anyone who gets it (it's inside the steps webhook URL) can act as that user, and clearing site data loses it. There's no recovery beyond the saved ID.
  • Abuse resistance is basic (per-IP signup limit, caps). A hostile crowd could still fill the 2000-user quota. It's a project, not a hardened service.
  • A cron run does a few database queries per ringing user, so very large numbers of simultaneous alarms would hit Cloudflare's free-tier limits.
  • The deployed code was tested offline. Push on a real iPhone is the part exercised only in live use.

Likely viva questions

Alarms aren't common to everyone. How does the app keep users separate without a login?

Each browser generates a random 128-bit ID and sends it with every request. All data is stored against that ID, so users can't see or change each other's alarms. It trades password-style accounts for zero friction: the ID is the credential, and losing it means losing the data, which is why the app offers copy and restore.

Why can't the app just read the Clock app's alarms?

iOS does not expose Clock alarms to third-party apps. There is no API to read, edit or observe them, so the app schedules and rings its own alarms.

Why use a Shortcut for steps instead of HealthKit directly?

HealthKit is native-only (Swift/Objective-C). A web app cannot call it. Shortcuts can read Health data and make an HTTP request, which gives the server a step count without writing a native app.

How is the shifted time hidden from the user?

It is computed and stored only in the Worker's database. The state API selects only the intended time and status, so the browser never receives the shifted time. A unit test asserts the response contains no fire time.

Why a Normal distribution with σ = 15·x?

It treats earlier and later symmetrically, gives small shifts for small x, and has unbounded tails as the brief asked. Scaling σ linearly makes x a clean "dial" for how much chaos you earn.

What does the 3-minute grace do?

It subtracts the first 3 minutes of ringing from x, so a normal human reaction time causes no shift. Only time beyond that counts.

What happens if I never respond to the alarm?

After 30 minutes it auto-stops, x is capped at 27 (σ = 405 min), and a new 24h clock starts from when it began ringing.

How does the alarm ring if the app is closed?

A Cloudflare cron runs every minute, starts any due alarm and sends Web Push notifications every ~30 seconds until you open the app and press Stop or Snooze.

What would you improve next?

A native iOS app with AlarmKit and HealthKit would give true ringing and live steps; a signed Shortcut link for one-tap setup; and real accounts (Sign in with Apple) so alarms survive clearing storage and work across devices.
